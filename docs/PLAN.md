# Adding OMEMO to Thunderbird Chat: Architecture & Roadmap

## Recommendation

Add OMEMO to Thunderbird's existing chat system rather than building a standalone client. This is not just the nicer outcome, it appears to be genuinely achievable: Thunderbird Chat's XMPP implementation is pure JavaScript, and Thunderbird ships a mechanism, WebExtension Experiments, that lets an add-on run privileged JS with full access to that internal code. A standalone client would mean re-implementing XMPP, roster/presence handling, MUC, account management, and the whole UI from scratch, essentially rebuilding Converse.js as a desktop app. Extending Thunderbird Chat means writing only the OMEMO layer and wiring it into machinery that already exists and already works.

## What we confirmed

Thunderbird's chat backend (the `chat/` directory of comm-central, inherited from Instantbird) implements protocols as JavaScript modules conforming to `prplI*` interfaces, registered through `jsProtoHelper`. XMPP is one of the "full" JS implementations (not a libpurple wrapper), living in `chat/protocols/xmpp/` across `xmpp.sys.mjs`, `xmpp-base.sys.mjs`, `xmpp-xml.sys.mjs`, `xmpp-session.sys.mjs`, and `xmpp-authmechs.sys.mjs`. GTalk and Odnoklassniki are thin subclasses of the same XMPP code. Matrix support, by contrast, leans on an external SDK rather than an in-tree implementation.

OMEMO has been an open, unassigned Bugzilla request (bug 1237416) for ten years. It is explicitly not on Thunderbird's 2026 desktop roadmap; the project is, in its own words, waiting on a volunteer. The core maintainer (Patrick Cloke) noted as recently as five months ago that the blocker has never really been willingness, it's been the lack of a JS/C/C++/Rust OMEMO implementation under a license Mozilla can ship (MPL/MIT/Apache/LGPL). The one mature JavaScript OMEMO library that exists, `libomemo.js` (used by Converse.js), is GPL-3.0, which is why it was never just dropped in. That licensing gap is exactly why building our own implementation, rather than reusing an existing one, is the right call here (more below).

Thunderbird already has precedent for bolting protocol-level encryption onto chat conversations without changing the wire protocol implementation: OTR support is a self-contained module (`chat/modules/OTR.sys.mjs`) that listens for `sending-message` and `received-message` notifications on the observer service, intercepts the outgoing/incoming message object, and rewrites its text in place. That module also exposes `Ci.prplIConversation.ENCRYPTION_NOT_SUPPORTED` as a signal so OTR can defer to a protocol's native encryption when one exists, which is precisely the flag OMEMO-for-XMPP would want to occupy. This gives us a proven pattern to extend rather than an unknown to invent, though OMEMO needs to go one layer deeper than OTR does (see below).

WebExtension Experiments are the add-on mechanism that makes any of this possible without a Thunderbird fork. An Experiment's implementation script is privileged the same way in-tree code is: it can `ChromeUtils.importESModule` any internal module (`IMServices`, the XMPP protocol modules, the observer service) and monkey-patch or subscribe to it directly. The tradeoff is that Experiments trade Thunderbird's normal permission model for a single "full, unrestricted access" prompt, and because they reach into undocumented internals, they can break across Thunderbird releases in ways a stable WebExtension API would not. That's a maintenance cost we should budget for, not a reason to avoid the approach, since there's no other way to reach chat internals today.

## Where OTR's pattern isn't quite enough

OTR can get away with swapping message text because OTR ciphertext is itself representable as a plain string sent inside `<body>`. OMEMO cannot do that: XEP-0384 requires adding a sibling `<encrypted>` element to the stanza (containing the ratchet header, one encrypted key per recipient device, and the AES-GCM payload) while replacing `<body>` with a plaintext warning for non-OMEMO clients. It also requires out-of-band traffic that has nothing to do with any single message: publishing our own device list and PreKey bundles to PEP (XEP-0060 personal eventing) nodes, and fetching a contact's device list and bundles before the first message to them. None of that fits through a "rewrite the message text" hook.

Practically, this means the add-on needs two layers: the `sending-message` / `received-message` observer pattern (or its modern equivalent) to know *when* to engage OMEMO for a given conversation, matching OTR's approach of checking `encryptionState`; and a lower, stanza-construction layer, reached by patching the XMPP account's outgoing stanza builder and incoming stanza dispatcher directly, to actually attach and read the `<encrypted>` element and to send/receive the PEP IQs. The exact function names for that second layer are now confirmed by reading the actual source (see Milestone 0 findings below), so this is no longer an open question, it's a concrete implementation target.

**Milestone 0 findings (source spike complete, done by reading `chat/protocols/xmpp/xmpp-base.sys.mjs`, `xmpp-session.sys.mjs`, and `chat/modules/jsProtoHelper.sys.mjs` directly from comm-central).** The 1:1 outgoing path is `GenericConversationPrototype.sendMsg()` (in `jsProtoHelper.sys.mjs`), which notifies observers on `"preparing-message"` then `"sending-message"` with an `OutgoingMessage` object (this is the exact object OTR mutates), and then calls `this.dispatchMessage(om.message, om.action, om.notification)`, an abstract method each protocol must implement. For XMPP specifically, `XMPPConversationPrototype.dispatchMessage(aMsg, aAction)` (in `xmpp-base.sys.mjs`) is a five-line function: it builds `const s = Stanza.message(this.to, aMsg, cs)` and calls `this._account.sendStanza(s)`. This is the real, clean encryption hook, not the message-text-rewrite trick OTR uses: our Experiment can monkey-patch `XMPPConversationPrototype.dispatchMessage` directly, intercept the plaintext, run it through the OMEMO ratchet, and construct our own stanza (plaintext warning `<body>` plus a sibling `<encrypted>` element per device) before calling the same `this._account.sendStanza()` primitive the original code uses. One wrinkle: the original also calls a local, non-exported helper `_displaySentMsg(this, aMsg)` for local echo, which our patched version can't call directly since it isn't exported from the module; we'll need to replicate that display step ourselves (likely via `this.writeMessage()`), which is a small, solvable detail rather than an open question.

On the incoming side, `GenericAccountPrototype`'s XMPP implementation of `onMessageStanza(aStanza)` (in `xmpp-base.sys.mjs`) already extracts `<body>` (preferring `<html><body>` over plain `<body>`) before handling MUC subjects, invitations, and XEP-0280 Message Carbons (carbons being already implemented in-tree is good news for our own multi-device sync later). The clean decryption hook is to wrap `onMessageStanza` and, before the original runs, check the raw stanza for a `<encrypted>` child in the oldmemo/twomemo namespace; if present, decrypt it and splice a synthetic `<body>` child into the stanza's existing `children` array (the `Stanza`/`XMLNode` objects are plain JS objects with a `.children` array and a `.getElement()` helper, so this splice is cheap) so the rest of the original function's logic, MUC subjects, carbons, delayed-delivery timestamps, keeps working unmodified.

One correction to our working assumption: Thunderbird's XMPP implementation does **not** already have PEP (XEP-0060 personal eventing) plumbing to reuse. Avatars use the older `vcard-temp` (XEP-0054/XEP-0153) mechanism (`_addVCardRequest`, `onVCard`, `parseVCard` in `xmpp-base.sys.mjs`), not pubsub. That means Milestone 3 (device list & bundle management) needs to build PEP publish/subscribe support from scratch, generic `<iq>` get/set stanzas with `<pubsub xmlns='http://jabber.org/protocol/pubsub'>` children and the matching disco#info feature/notify advertisement, rather than extending existing bookmark or avatar code as originally assumed. This is straightforward given `Stanza.iq()`/`Stanza.node()` helpers already exist and `account.sendStanza()` supports a response callback keyed by stanza id, but it's real, uncounted work that should get its own line item, not be folded silently into Milestone 3.

## Protocol version target

XEP-0384 has had three practically distinct generations, and it's worth being precise since "OMEMO" alone is ambiguous. Versions 0.2-0.3 use the `eu.siacs.conversations.axolotl` namespace ("legacy"/"oldmemo") and, despite being old, are still the widest-deployed baseline because Conversations, Cheogram, and Snikket defaulted to it for years. Versions 0.4-0.7 introduced `urn:xmpp:omemo:1`, which saw little real adoption and is largely dead. Versions 0.8+ use `urn:xmpp:omemo:2` ("twomemo"), which is the current spec (since late 2021) and what newer clients are converging on. Reference implementations like `python-omemo` handle this by supporting oldmemo and twomemo as swappable backends and skipping omemo:1 entirely.

Given that, "modern namespace plus legacy fallback" should mean targeting **oldmemo (`eu.siacs.conversations.axolotl`) and twomemo (`urn:xmpp:omemo:2`)**, not the intermediate `omemo:1`. This gives real interoperability with the actual client population (Conversations, Cheogram, Snikket, Gajim, Dino, BeagleIM) without spending effort on a namespace almost nobody kept using. The two backends mostly share the X3DH/Double Ratchet core; the difference is in KDF/AD construction and a few wire-format details, so supporting both is closer to "two encoders" than "two crypto stacks."

## Crypto approach

Recommendation: implement X3DH and the Double Ratchet ourselves on top of audited, permissively-licensed primitives, specifically `@noble/curves` (Curve25519/X25519/Ed25519) and `@noble/ciphers` (AES-GCM, HKDF), both from the well-regarded `noble` cryptography suite (audited, no dependencies, MIT-licensed). This costs more upfront than reusing `libomemo.js`, but buys three things that matter given the long-term goal is genuinely undecided: an MIT/permissive license that doesn't foreclose ever proposing this for inclusion in Thunderbird itself, the ability to implement current oldmemo/twomemo wire formats precisely rather than inheriting an older library's assumptions, and no GPL-vs-MPL entanglement questions if this ever gets bundled or linked against other MPL-licensed Thunderbird code.

The one genuinely tricky piece is XEdDSA, the construction OMEMO uses to reuse a single Curve25519 key pair for both X25519 ECDH and Ed25519-style signing. `noble-curves` supports the underlying curve conversions (`edwardsToMontgomery` and friends) but XEdDSA itself isn't a library function; it needs to be implemented directly from Signal's XEdDSA/VXEdDSA specification, which is a well-documented, moderate amount of work rather than an open research problem.

## Scope for v1

One-to-one chats only. Group chat OMEMO (MUC) adds real complexity on top: rooms must be non-anonymous so real JIDs are known, and every outgoing message fans out to every device of every occupant, which multiplies key-wrapping overhead and creates its own membership-change edge cases. Shipping 1:1 first gets a usable, correct encryption path in front of users and de-risks the harder MUC work for a v2.

## Licensing note

Decision: MPL-2.0, source public on GitHub. This keeps the door open to proposing it for comm-central later without a relicensing exercise, lets Mozilla (or anyone) actually look at and reuse the code, and matches the norm in the OMEMO/XMPP client world where every mainstream client is open source, which matters for a security tool people are trusting with their message content.

## Monetization & distribution strategy

_Revised 2026-09-26. The original plan (public source plus a paid, signed build listed on addons.thunderbird.net) is dropped: ATN rejects Experiment-based add-ons, and this add-on can't work without an Experiment, since Thunderbird's official add-on APIs have nothing for chat._

- **Source:** public on GitHub under MPL-2.0 once the crypto passes interop tests, so anyone can build it and Mozilla can adopt it directly.
- **Builds:** self-distributed unsigned `.xpi` files (GitHub releases), installed from file. Users set `xpinstall.signatures.required=false` in the Config Editor, as Daynizer's users do.
- **Charging:** **Decided 2026-09-26 (the maintainer):** the OMEMO add-on as it stands is released **free** (MPL-2.0, public), in the hope that Thunderbird adopts it, with the README asking for donations through a button to the maintainer's sponsors page (`.github/FUNDING.yml`). A second, paid **Pro** version adds calling (milestone 8) for **$10**. Since the free repo is public, Pro's calling code lives in a separate private repo under the maintainer's own license (MPL-2.0 is per file, so new files can be proprietary; any MPL file Pro changes must have its source offered to Pro's buyers). Plan: generic extension points in the free repo, the calling code in Pro's own files.
- **Sunset:** the add-on is a bridge until Thunderbird ships native OMEMO (bug 1237416). Say so in the README and release notes.

### Tipping via GitHub

GitHub supports a sponsor/tip button natively through a `.github/FUNDING.yml` file in the repo, no separate infrastructure needed. It can point at GitHub Sponsors (requires a one-time application/approval), and/or no-approval-needed options like Ko-fi, Liberapay, Patreon, Open Collective, or a plain custom URL (e.g. a PayPal.me link). Once the file is merged to the default branch, GitHub shows a "Sponsor" button on the repo automatically. Add this in the packaging milestone below alongside the GitHub release setup.

## Milestones

_Milestones 2-4 are broken into concrete tasks in `docs/TASKS.md` (2026-09-24). Progress: `docs/STATUS.md`. As of 2026-09-26, milestones 0-4 are done and confirmed in Thunderbird, milestone 5 (trust) is working, milestones 6-7 are done (0.1.0 released 2026-09-26), and milestone 8 (calling, the paid Pro version) is open._

**0. Source spike (1-2 weeks).** Read `xmpp.sys.mjs`, `xmpp-base.sys.mjs`, and `xmpp-xml.sys.mjs` in full to find the actual stanza-build and stanza-dispatch entry points, confirm whether PEP/pubsub helpers already exist in-tree (likely, since avatars and bookmarks use PEP) or need to be added, and confirm the exact shape of the `sending-message`/`received-message`/`update-conv-encryption` observer contracts by tracing how OTR uses them today. This milestone produces the real integration-point list the rest of the plan currently has to guess at.

**1. Experiment scaffold.** A minimal WebExtension with an `experiment_apis` entry that can import `IMServices` and the XMPP modules, log every outgoing/incoming stanza for an XMPP account, and prove the monkey-patch approach survives a Thunderbird restart and an account reconnect.

**2. Crypto core.** X3DH key agreement, Double Ratchet session state, and XEdDSA signing/verification, implemented against `@noble/curves`/`@noble/ciphers`, with unit tests against known-answer test vectors (Signal's public X3DH/Double Ratchet test vectors, adapted for OMEMO's AD construction).

**3. Device list & bundle management.** Publish our own device ID to the appropriate PEP devicelist node, generate and publish a PreKey bundle (identity key, signed PreKey, one-time PreKeys), and fetch a peer's device list and bundles on first contact, for both oldmemo and twomemo namespaces.

**4. Wire the crypto into the stanza pipeline.** Encrypt outgoing `<body>` into a per-recipient-device `<encrypted>` element at send time; decrypt incoming `<encrypted>` elements and hand plaintext to the existing conversation/UI layer at receive time. This is where milestone 0's findings get used directly.

**5. Trust UI.** `GenericConversationPrototype` (in `jsProtoHelper.sys.mjs`) already exposes a generic `encryptionState` getter (default `Ci.prplIConversation.ENCRYPTION_NOT_SUPPORTED`) and an `initializeEncryption()` method, plus an account-level `encryptionStatus` property that fires an `"account-encryption-status-changed"` observer notification, all of which is real, pre-existing UI plumbing for protocol-native encryption (this is the same surface Matrix's native encryption work, referenced in bug 1237416, hooked into). Overriding these on the patched XMPP conversation object, rather than inventing new UI chrome, should get us most of the "this conversation is encrypted" indicator for free; still need to verify how much the actual XUL/HTML conversation UI renders from these values today, since Matrix may be the only protocol currently exercising them. Fingerprint display and manual verification (TOFU by default, like most clients ship initially) sits on top of that.

**6. Hardening & multi-device.** Handling our own multiple devices (desktop add-on plus phone clients like Conversations/Cheogram), stale/removed device cleanup, and PreKey replenishment.

**7. Packaging & distribution (revised 2026-09-26).** Make the repo public with its MPL-2.0 license and a `.github/FUNDING.yml` for tips; publish unsigned `.xpi` builds as GitHub releases with install steps (install from file, `xpinstall.signatures.required=false`); if the maintainer decides to charge, a paid download on Gumroad as well; maintain a compatibility matrix of validated Thunderbird versions, since Experiments aren't guaranteed stable across releases; state the sunset plan (a bridge until Thunderbird ships native OMEMO) in the README; and add a "What this add-on can access" section to the README and the Instructions tab explaining Thunderbird's "full, unrestricted access" warning (shown for every Experiment add-on; it means anything the user's own account can do, not admin) against what the add-on actually uses (the chat hooks, its `<profile>/omemo/` key files, the existing XMPP connection). No ATN submission: ATN rejects Experiment add-ons.

**8. Calling (after v1; added 2026-09-25).** Audio (then video) calls with Jingle, interoperating with Conversations, Cheogram, Snikket, Dino and Monal: Jingle signaling (XEP-0166, XEP-0167 RTP sessions, XEP-0176 ICE-UDP, XEP-0320 DTLS-SRTP fingerprints), Jingle Message Initiation (XEP-0353) to ring all devices, and STUN/TURN from the server via XEP-0215 (Snikket ships TURN). The big win for the maintainer: Cheogram/JMP bridge phone calls to Jingle, so this would bring JMP phone calls to Thunderbird. Feasibility checked on the maintainer's Thunderbird 156: `RTCPeerConnection` and `navigator.mediaDevices.getUserMedia` both exist in the add-on's background page, so the media side can be standard WebRTC in an add-on window, with only the signaling going through the same XMPP hooks as OMEMO (one add-on, one set of hooks, so they don't fight). OMEMO can then verify the call's DTLS fingerprint the way Conversations does. Audio first; call window, ringing, device selection and TURN are most of the work.

## Open risks worth tracking

Thunderbird's internal chat APIs are not a stable, versioned surface, so upgrades to Thunderbird itself may require patching the Experiment's implementation script; this is the standard cost every Experiment-based add-on pays, not something specific to this project. MUC support, KDE Connect SMS bridging, Beeper/Matrix, and additional protocols are all real ideas worth returning to, but are explicitly out of scope until 1:1 XMPP OMEMO is solid, matching the "start simple" instinct already expressed.
