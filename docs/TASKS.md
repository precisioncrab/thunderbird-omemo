## Baseline (2026-09-24, first `npm install` + `npm test`; historical)

- Installed: `@noble/curves` 1.9.7, `@noble/hashes` 1.8.0, `@noble/ciphers` 0.6.0. Every API name marked `TODO(verify)` in `src/crypto/` resolves and works on these versions. Several are deprecated aliases in 1.9 and removed in 2.x (see 2.11).
- `npm test`: 1 pass, 3 todo. The script needed a fix first (Node 22+ wants a glob, not a directory).
- A throwaway probe went beyond the test:
  - **Double Ratchet state machine works:** in-order, out-of-order (3,1,2), both directions with key rotation, a late message from a previous chain, and tamper rejection.
  - **XEdDSA bug:** signatures verify as Ed25519 against their own public key, but `calculateKeyPair` doesn't clamp the private key. For a raw X25519 key the Edwards key doesn't match the X25519 public key (0/20 random keys; 20/20 when pre-clamped), so peers would reject our signed prekey. Fixed in 2.1.
  - `xeddsa.verify` (done in 2.3) and `x3dh.respondToHandshake` still threw (not implemented).
- **Biggest gap:** the message-layer crypto matches neither namespace. The code uses AES-GCM with a header-derived nonce and made-up HKDF info strings. Both oldmemo and twomemo use AES-256-CBC plus a truncated HMAC with keys expanded from each message key, protobuf-encoded messages, and a separate payload-encryption layer on top of the ratchet. The ratchet's state machine can stay; its KDF constants, cipher, and wire encoding get replaced (2.4-2.8). The 2.2 vectors have since confirmed the constants; see the table below.

## Per-namespace constants

Confirmed 2026-09-24 in task 2.2. Rows marked **tested** are checked by known-answer tests for both namespaces (`test/vectors.test.js`; X3DH in `test/x3dh.test.js`). Every twomemo row is backed by python-twomemo (MIT): its vectors hold the bytes, and their tests come with 2.5-2.8. For oldmemo the vectors cover only the key schedule (see the note under the table).

| | oldmemo (`eu.siacs.conversations.axolotl`, libsignal) | twomemo (`urn:xmpp:omemo:2`) |
|---|---|---|
| Public key encoding | `0x05` + X25519 u (33 B), identity key included | identity key in Ed25519 form (32 B, either sign bit); other keys X25519 (32 B) |
| X3DH input (**tested**) | `0xFF`x32 + DH1 + DH2 + DH3 + DH4 | same |
| X3DH HKDF (**tested**) | salt 32 zero bytes, info `WhisperText`, 32 B = root key | salt 32 zero bytes, info `OMEMO X3DH`, 32 B = root key |
| Associated data (**tested**) | initiator IK + responder IK (33 B each) | initiator IK + responder IK (Ed25519 form, 32 B each) |
| AD order per message | **sender IK + recipient IK**, so the responder's side swaps it (undocumented libsignal behavior) | initiator + responder for the whole session |
| Session start | root key = X3DH secret; the initiator does one DH ratchet step against the responder's signed prekey before its first message | same |
| Root KDF (**tested**) | HKDF, salt = root key, input = DH output, info `WhisperRatchet`, 64 B = new root key + chain key | same, info `OMEMO Root Chain` |
| Chain KDF (**tested**) | HMAC(CK, `0x01`) = message key, HMAC(CK, `0x02`) = next CK | same |
| Message key expansion | HKDF, salt 32 zero bytes, info `WhisperMessageKeys`, 80 B = AES key 32 / MAC key 32 / IV 16 | same, info `OMEMO Message Key Material` |
| Ratchet message cipher | AES-256-CBC (PKCS#7); MAC = HMAC-SHA-256(MAC key, AD + framed message) truncated to 8 B | same, MAC truncated to 16 B |
| Ratchet message framing | `0x33` + protobuf {dh_pub=1 (`0x05` + key), n=2, pn=3, ciphertext=4}, then the 8 B MAC appended | protobuf `OMEMOAuthenticatedMessage` {mac=1, message=2}, where message = protobuf `OMEMOMessage` {n=1, pn=2, dh_pub=3, ciphertext=4} |
| Key exchange framing | `0x33` + protobuf {pk_id=1, ek=2, ik=3, message=4 (the framed ratchet message), registration id=5 (unused), spk_id=6} | protobuf `OMEMOKeyExchange` {pk_id=1, spk_id=2, ik=3, ek=4, message=5 (nested `OMEMOAuthenticatedMessage`)} |
| Body encryption | AES-128-GCM, random 16 B key, 12 B IV sent in `<iv>`; ratchet encrypts key + 16 B tag (32 B) | random 32 B key, HKDF (zero salt, info `OMEMO Payload`, 80 B), AES-256-CBC, HMAC over the ciphertext truncated to 16 B; ratchet encrypts key + HMAC (48 B). The XEP-0420 envelope around the body is built one layer up; the vectors encrypt raw text |
| Empty message | no `<payload>`; ratchet encrypts 16 random bytes | no `<payload>`; ratchet encrypts 32 bytes |
| Signed prekey signature (**tested**) | over the 33 B encoded key; the signer's Ed25519 sign bit rides in the top bit of the signature's last byte | over the 32 B key; plain Ed25519 verify against the published identity key |

**oldmemo note:** no permissively licensed oldmemo implementation exists, so `oldmemo.json` comes from the generic MIT X3DH/Double Ratchet libraries with oldmemo's constants and covers only the key schedule. The oldmemo rows not marked tested (per-message AD order, key encodings in messages, framing, body encryption, empty messages) and the bundle sign-bit convention come from the first reference run and libsignal's known behavior. The current vectors don't cover them; task 4.12 confirms them against real clients.

## Milestone 4: wire crypto into the stanza pipeline

**Goal:** 1:1 messages round-trip encrypted between Thunderbird and real OMEMO clients, in both directions and both namespaces. **Done when** the 4.12 interop matrix passes.

**Done ahead of the tasks below (2026-09-25):** the message layer, `src/omemo/messages.js`, which is the crypto side of 4.3, 4.7, 4.9 and 4.10. `encryptMessage` encrypts the body once and its key material per device, starting sessions from bundles (random pre key) and wrapping messages in the key exchange until the peer replies; devices it can't reach are reported, not fatal. `decryptMessage` finds our key, starts a session from a key exchange or reuses it when the same key exchange repeats (sessions remember the peer's base key), clears our pending key exchange on any reply, removes and refills a used pre key, and opens the payload (twomemo: envelope with sender check). It returns `sessionStarted` (send an empty message back, 4.10) and `preKeyUsed` (republish the bundle), and fails with `OmemoError` codes for 4.9's notices, leaving the store untouched on failure. Tested end to end with stores exchanging serialized XML in both namespaces: repeated key exchanges, confirmation, several devices including our own, empty messages, replays, a reinstalled peer, tampering. Trust decisions stay with milestone 5 (results carry the peer's identity key). What's left in these tasks is the Thunderbird side: the send queue, stanzas, carbons, local echo and UI.

**Thunderbird side written 2026-09-25 (version 0.0.4), limited to test1 and test2:** The maintainer chose to encrypt only conversations between test1@ and test2@test.snikket.chat for the first test builds, so 4.1's policy is for now an allowlist (`ENCRYPTION_ALLOWLIST` in `src/experiment/implementation.js`, `encryptionAllowlist` in the bridge), applied in both directions: outside it nothing is encrypted, decrypted or sent automatically. Inside it, `src/omemo/bridge.js` does 4.2 (per device since 0.0.5: twomemo if the device is on that JID's twomemo list, else oldmemo, with one `<encrypted>` per namespace in the same stanza, because Conversations-based clients such as Cheogram only speak oldmemo), 4.3 (a per-conversation queue; devices and bundles fetched as needed; our own other devices included), 4.4 (fallback body, `<encrypted>`, store hint, EME), 4.5 (local echo like `_displaySentMsg`, flagged `isEncrypted`), 4.6 (sent and received carbons), 4.7/4.8 (decrypt in place, body swapped), 4.9 (a notice per `OmemoError` code instead of the fallback; a message that can't be encrypted is not sent and the conversation says so), 4.10 (empty messages swallowed; a new session gets an empty confirmation back) and 4.11 (the store saves after every change). Tested with two fake Thunderbird accounts exchanging real stanzas. Since 0.0.6 the indicator uses Thunderbird's own encryption UI (conversation `encryptionState`/`initializeEncryption`, padlocks via `isEncrypted`), and a per-contact opt-in switch is built but off (`optIn`). Confirmed in Thunderbird with real Cheogram phones in both directions (0.0.5). Not done: turning opt-in on (the maintainer's call), verification/TRUSTED (M5), 4.12's full matrix.
